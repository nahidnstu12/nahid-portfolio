Environment variables (your server)

Never commit secrets. Use .env locally and Hetzner env / secrets file in prod.

# App
NODE_ENV=production
PUBLIC_APP_URL=https://yourdomain.com

# Database
DATABASE_URL=postgresql://...

# Redis / queue
REDIS_URL=redis://...

# Auth (Better Auth — names may match your config)
BETTER_AUTH_SECRET=<random 32+ bytes>
BETTER_AUTH_URL=https://yourdomain.com

# Encrypt Page tokens at rest
TOKEN_ENCRYPTION_KEY=<32-byte key>

# Meta (platform — one app for all tenants)
META_APP_ID=
META_APP_SECRET=
META_WEBHOOK_VERIFY_TOKEN=<you invent this string>

# LLM (POC: Groq only — one provider, one client module)
LLM_PROVIDER=groq
LLM_MODEL=<model id with reliable tool calling>
GROQ_API_KEY=

# Optional later — swap LLM_PROVIDER + LLM_MODEL, no code change
# DEEPSEEK_API_KEY=
# MOONSHOT_API_KEY=
# ANTHROPIC_API_KEY=

Merchant Page tokens go in Postgres encrypted, not in env — one row per connected Page.

Groq setup (initial LLM)

  1. Sign up at console.groq.com → create API key.
  2. Pick a model with tool / JSON reliability for your agent (test Bengali + search_products calls).
  3. Set GROQ_API_KEY on worker (and Next if agent runs there).
  4. Monitor usage on Groq dashboard; upgrade only when free RPD/RPM blocks pilots.
  1. Log every prompt, tool call and reply to Postgres — at commercialization this log is the eval set for choosing the production model.
Groq is the POC decision — don't revisit it mid-build All model calls go through one module (lib/llm.ts) exposing chat(messages, tools); nothing else imports the provider SDK. Model name lives in LLM_MODEL. Tool schemas stay provider-neutral JSON Schema. Swapping to a stronger model later is an env change plus a re-run of the eval set — not a refactor.
Known weak spot to watch Banglish (romanized Bangla) is where small open models are weakest, and it is the majority of real traffic. Test search_products tool selection on real Banglish messages early — if tool choice is unreliable, that is a model problem, not a prompt problem, and it is the one reason to revisit this decision before the pilot.

Webhook configuration

  1. Public HTTPS URL, e.g. https://yourdomain.com/api/webhooks/meta
  2. In Meta app → Messenger → Webhooks: paste URL + verify token → subscribe your test Page
  3. Subscribe fields (POC): messages, message_echoes, feed, optionally messaging_postbacks
  4. Implement GET handler: echo hub.challenge when verify token matches
  5. Implement POST: validate X-Hub-Signature-256 with App Secret → enqueue job → return 200 quickly
FieldGives youWhy the POC needs it
messages Inbound customer DMs The main pipeline
message_echoes Copies of messages sent by the Page — including ones the merchant typed in Facebook's own inbox Without it the bot replies on top of a human. Tag your own sends by message_id and ignore those; a merchant-typed echo switches the thread to human.
feed Comments on the Page's posts Comment → DM. Filter to comment-add on own posts; ignore the Page's own comments. 
Send a DM
POST https://graph.facebook.com/v21.0/{PAGE-ID}/messages
  ?access_token={PAGE_ACCESS_TOKEN}
Body: recipient { id: PSID }, message { text: "..." }

Private reply to a comment (opens a Messenger thread)
POST https://graph.facebook.com/v21.0/{COMMENT-ID}/private_replies
  ?access_token={PAGE_ACCESS_TOKEN}
Body: message = "..."

Optional public reply on the same comment
POST https://graph.facebook.com/v21.0/{COMMENT-ID}/comments
  ?access_token={PAGE_ACCESS_TOKEN}
Body: message = "Inbox check korun"

Use the current Graph API version from Meta docs. Standard replies: the customer must message first; 24-hour messaging window after their last message. Private reply is allowed once per comment and only within Meta's documented window after the comment — confirm the current limit before building, and make the call idempotent on comment_id because Meta retries webhooks.

Connect Facebook (merchant flow — no keys from them)

  1. Redirect to Facebook Login with your App ID + requested scopes
  2. Merchant selects Page and clicks Allow
  3. Exchange code server-side → short-lived user token → long-lived → Page access token
  4. Store page_id + encrypted page_access_token on tenant row
  5. Subscribe that Page to your app webhooks (Graph call with Page token)

Valid OAuth Redirect URIs in Meta app must include e.g. https://yourdomain.com/api/connect/facebook/callback (match your Better Auth / custom route).

Go-live checklist (before pilot merchant)

  • PUBLIC_APP_URL HTTPS works; Meta webhook shows green / receives test event
  • Webhook signature verification enabled (reject bad POSTs)
  • Test Page connected; inbound DM appears in Inbox
  • Human can send reply from dashboard → customer sees it in Messenger
  • Reply typed in Facebook's own Page inbox switches the thread to human — bot stays silent
  • Our own outbound messages do not trigger the echo takeover (own message_id tagged and ignored)
  • Comment on a test post → private reply arrives; replaying the same webhook sends no second reply
  • Two DMs sent 200ms apart produce one ordered exchange, not two overlapping agent runs (per-conversation lock works)
  • Image or voice attachment → thread flips to pending_human, no AI reply attempted
  • ≥1 confirmed product + shop rules → AI toggle enabled
  • Groq key on worker; test tool call returns real price from DB
  • Banglish smoke test: dam koto / M size ache / delivery charge koto answer correctly from the catalog
  • Page tokens encrypted; App Secret not in client bundle
  • Meta Business Verification submitted (or done); app Live + permissions approved — otherwise pilot stays on a test Page in Dev mode
