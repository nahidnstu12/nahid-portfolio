Messenger MVP / POC plan Implementation

Scope: Bangladesh · one Page · Messenger DM + comment→DM · one vertical (e.g. fashion) · one inbox per tenant

← Brainstorm User flows → Setup guide → All ideas

POC outcome (what “done” looks like)

One pilot merchant connects their FB Page; customers DM on Messenger or comment on a post; AI answers product/price/delivery in Banglish / Bangla / English using the confirmed catalog; collects variant, qty, phone, address into a lead; uncertain threads go to human inbox without double replies.

  • Connect Page + webhook (messages, message_echoes, feed)
  • CSV / paste-link import → merchant confirms prices & delivery rules
  • AI + tools (not raw LLM for price/stock)
  • Comment on post → private reply → same AI thread
  • Lead capture + human takeover (including takeover triggered by the merchant using Facebook's own Page inbox)

Out of POC: WhatsApp, website widget, payments, auto-orders, CRM, multi-Page, billing (optional stub only), image and voice-note understanding (attachment → straight to human).

Not a goal: feature parity with any existing tool. This build exists to prove the pipeline on real BD traffic.

Public URL → Meta webhook + Facebook OAuth redirect URIs must match.

LLM decision (settled): Groq for the whole POC. Do not spend POC time comparing providers — the pipeline is the deliverable.

  • All model calls go through one module (lib/llm.ts): chat(messages, tools). Nothing else imports the provider SDK.
  • Model name lives in env (LLM_MODEL), not in code.
  • Tool schemas are provider-neutral JSON Schema — reusable as-is on any OpenAI-compatible or Anthropic-style API.
  • Log every prompt + tool call + reply. That log becomes the eval set when a better model is chosen at commercialization.

Choose the production model after the pilot, scored on the real messages the POC collected — not on guesses now.

Comment job: optional public reply → Private Reply API
  → creates/looks up conversation → continue as a normal thread

Worker (one job at a time per conversation_id — Redis lock):
  load thread + mode (bot|pending_human|human)
  → attachment (image/audio)? → pending_human, notify, stop
  → if human/pending_human: notify inbox only, no auto reply
  → if bot: run agent (tools) → send reply OR set pending_human
Outbound: re-read mode immediately before Send API

Every outbound message we send also comes back as a message_echoes event. Tag our own sends (store the returned message_id) so an echo of our own reply is ignored and only a merchant-typed echo triggers takeover.

Implementation phases (POC → first MVP)

Order is strict: later phases assume earlier exit criteria. Estimates assume 1–2 devs; adjust weeks to your pace.

Phase 0 (day 1, runs in background): start Meta Business Verification — business documents, verified domain, privacy-policy URL, data-deletion callback URL. It takes weeks and is independent of code. Do not discover this in Phase 7.

Phase 1 SaaS shell + data model ~1 week
  • Monorepo or single repo: Next.js + Ant Design shell; Prisma schema (tenants, users, pages, products, variants, shop_rules, conversations, messages, leads)
  • Better Auth wired to Prisma user/session tables; tenant membership on signup
  • Local/docker: Postgres + Redis; BullMQ worker skeleton (no-op job)
  • Dashboard routes: Catalog · Inbox · Settings · Connect (placeholder pages)
  • Seed one fake tenant for local dev
Exit: Merchant can log in and CRUD a product manually (no Meta yet).
Phase 2 Catalog + shop rules (confirmed-only) ~1 week
  • CSV import template (name, price, sizes, stock, sku optional)
  • Product editor + “Confirm catalog item” bulk action
  • Shop rules form: flat delivery fee, COD, free-text policies
  • Optional: paste FB post URL → draft row (Graph API with Page token in Phase 3; manual paste text OK for POC start)
  • Tool layer stubs: search_products, get_product, get_delivery_quote (reads DB only)
Exit: Tools return correct BDT price/stock for confirmed products only; drafts invisible to agent.
Phase 3 Meta Messenger — receive only ~1 week
  • Meta app (dev → later Live): Facebook Login for Business, pages_messaging, pages_manage_metadata, pages_show_list, plus pages_read_engagement / pages_manage_engagement for comments in Phase 6 (validate current permission names in Meta docs)
  • Connect flow: OAuth → select Page → save token encrypted
  • Subscribe Page to app + register webhook URL; verify token challenge
  • Subscribe fields: messages, message_echoes (feed comes in Phase 6)
  • Parse inbound messages → store in messages; show in Inbox UI (no AI yet)
  • Idempotency on message.mid
  • Detect attachments (image / audio / file) and flag the message — no parsing, just a flag the agent will honour later
Exit: Real customer message appears in dashboard within seconds; webhook retries don’t duplicate rows; a reply typed by the merchant in Facebook's own Page inbox also shows up (via echo) in your timeline.
Phase 4 Send path + conversation state ~3–5 days
  • Send API from dashboard (human types reply) — proves token + threading
  • Per-conversation mode: bot | pending_human | human; assignee optional
  • “Take over” / “Release to bot” in UI updates mode
  • Worker checks mode immediately before any automated send
  • Redis lock per conversation_id around the job — plain BullMQ has no per-key serialization (that is BullMQ Pro “Groups”), so two fast messages will otherwise process concurrently
  • Echo-driven takeover: store the message_id of everything we send; a message_echoes event we did not send means the merchant replied from Facebook's own inbox → set human
Exit: Human can reply from inbox; mode prevents bot send while human active; replying from the Facebook Page inbox silently switches the thread to human mode.
Phase 5 AI agent (Banglish / Bangla / English) + lead capture ~2 weeks
  • Agent via Groq through lib/llm.ts: tool-calling loop; system prompt — fashion vertical, never invent price
  • System prompt states the language rule explicitly: reply in the same script/style the customer used; Banglish in → Banglish out
  • Agent loop: classify intent → tool calls → reply; max turns per inbound message
  • Slot collection: variant, qty, phone, address → write/update leads row linked to conversation
  • Confidence rules → pending_human + notify inbox: no product match, price question with empty catalog, angry/opt-out keywords, any image or voice attachment
  • Log every prompt, tool input/output and reply on the message row — this is both the audit trail and the future eval set
Exit: Replay ~200 real messages pulled from the pilot merchant's existing Page inbox (not scripted ones) through the agent offline. Zero wrong prices; correct tool chosen on the common intents; Banglish replies read naturally to a native speaker. Lead row complete when the customer gives an address.
Phase 6 Comment → DM ~4–5 days
  • Subscribe Page webhook field feed; filter to comment-add events on the Page's own posts
  • Ignore: comments by the Page itself, replies to our own comment, edits/deletes
  • Idempotency on comment_id (Meta will retry)
  • Optional public reply on the comment (short, fixed text — merchant-editable, e.g. “Inbox check korun”)
  • Private Reply API on the comment → opens/uses the Messenger thread with that user
  • Map comment → the same conversation row as a DM from that PSID; record source: comment | dm
  • Seed the thread with the post context so the agent knows which product is being asked about
  • Respect the limits: one private reply per comment, only inside Meta's allowed window; after that the ordinary 24-hour messaging window applies
  • Merchant kill switch: comment auto-reply on/off in Channel settings
Exit: A comment saying “dam koto” on a real post produces a private reply within seconds, the resulting thread runs through the same agent + tools + state machine as a DM, and a repeated webhook does not send a second private reply.
Phase 7 POC pilot (design partner) ~2 weeks parallel
  • One fashion Page owner in BD; you onboard catalog together (paste post links + CSV + confirm)
  • AI on limited hours or “supervised” (you watch inbox daily)
  • Track: auto-resolved vs human; lead count; comment→DM conversion; factual errors (must be zero on price/stock)
  • Keep a running list of the real Banglish intents seen — this is the main asset the POC produces
  • Meta app Live + app review if pilot uses production Page (stay on a dev/test Page if review is slow)
Exit: Merchant says the inbox saves time; you have a real intent list + error log; you have a logged message corpus to evaluate a better model against.
Phase 8 Harden (post-POC, before a second merchant) after POC exit
  • Model decision: score Groq against stronger candidates on the logged real messages; swap via LLM_MODEL if it wins
  • Image handling: vision model → product match, replacing attachment→human
  • Onboarding checklist UI (connect → import → confirm → enable AI)
  • Rate limits + AI kill switch per tenant
  • Basic analytics: messages/day, leads/week, human takeover rate, comment→DM conversion
Exit: Second merchant can self-serve connect + catalog with <30 min of your support.

Risks to watch during POC

  • Business Verification / app review delay — start day 1; use a test Page + test users until Live.
  • Merchant uses Facebook's own Page inbox — without message_echoes the bot talks over the human. Highest-visibility failure; handled in Phase 4.
  • Double reply from concurrency — outbound gate on conversation mode plus a Redis lock per conversation_id. Plain BullMQ does not serialize per key.
  • Duplicate private replies — Meta retries feed events; a private reply is allowed once per comment. Idempotency on comment_id is mandatory, not optional.
  • Banglish quality — the failure mode is a fluent, wrong-toned or wrong-tool reply. Evaluate on real inbox messages, never on scripted ones.
  • Attachments — image/voice must route to human in the POC. An agent that silently ignores an attached photo looks broken to the customer.
  • Empty catalog — block “Enable AI” until ≥1 confirmed product + delivery rule saved.
  • Bangla numbers — normalize ১২৯০ / 1290 in the tool layer before compare.
