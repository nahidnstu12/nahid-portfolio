Product vision (original brainstorm)

SaaS যেখানে shop owner Facebook Page / WhatsApp connect করে — customer message Meta API webhook দিয়ে আপনার server-এ আসে, AI knowledge base দিয়ে reply দেয়; customer জানবে না backend AI।

Core insight: You are not building Messenger or WhatsApp. You connect the merchant’s account to your SaaS via Meta’s official APIs; inbound webhooks → AI → Send API back.

One agent, many channels Same AI agent can eventually serve website chat, Facebook Messenger, and WhatsApp — unified inbox + shared catalog/FAQ.
Scope right now: POC, Bangladesh only, one Page Not competing with anyone yet — no feature parity target, no multi-channel, no billing. One pilot merchant, one Facebook Page, Messenger + comment replies, Bangla/Banglish. Build the pipeline (webhook → queue → agent → tools → send → audit) correctly; everything else is swappable later.

Comment → DM (the real f-commerce funnel)

In Bangladesh most buying intent does not start as a DM. It starts as a comment under a boosted post — "price?", "dam koto", "inbox korun". The merchant then manually inboxes each commenter. That manual step is the highest-volume, most repetitive work in an f-commerce Page, and it is the strongest single reason a merchant would install this.

Customer comments on Page post
    │
Meta webhook (Page `feed` field)
    │
Your SaaS  ──► optional public reply ("inbox e reply dilam")
    │
Private Reply API → opens Messenger thread
    │
AI Agent (same agent, same tools, same state machine)
    │
Normal DM conversation + lead capture
Rules to respect Private reply is allowed once per comment and only within a limited window after the comment (Meta documents the current limit — verify before build). It needs comment-read/engagement permissions in addition to pages_messaging. Once the private reply lands, the thread follows the ordinary 24-hour messaging window.

Implementation note: a comment event and a DM event should converge on the same conversation record and the same mode state machine. Comment → DM is an entry point, not a second pipeline.

BD market reality (what customers actually send)

The plan originally assumed "Bangla or English text". Real Page inboxes are messier. This table is the input model the agent must be built against.

Input typeHow commonPOC handling
Banglish — romanized Bangla (dam koto, eta ache, delivery charge koto) Majority of messages Must work. This is the primary language target, not a variant of Bangla.
Bangla script Common Must work. Normalize Bangla numerals before any tool compare.
English Minority Works free.
Mixed in one message (ei dress ta M size ache?) Very common Must work — do not language-detect and branch; one prompt handles all.
Photo — screenshot of a post, or a product image forwarded with "eta?" Frequent Out of POC. Detect attachment → pending_human immediately. Do not let the agent guess.
Voice note Frequent Out of POC. Same: attachment → pending_human.
Sticker / emoji / single "hi" Common Short greeting reply; don't call tools.
Do not benchmark the model on invented messages Before locking the agent prompt, pull ~200 real messages from the pilot merchant's existing Page inbox and score two things only: (1) did it pick the right tool, (2) is the Bangla/Banglish reply natural. Scripted test DMs will pass and real traffic will fail.

Key correction “Connect and every message is auto-handled” is directionally right but incomplete. Messenger needs a Live app, Business Verification, Page permissions and webhook subscription; the merchant's own use of the native FB inbox must be detected via message_echoes; comment replies are a separate permission and a separate API with its own once-per-comment limit. Product UI should explain this, not hide it.

Verdict

Architecture is proven; MVP is buildable. Hard parts: channel onboarding, product truth (price/stock), operator workflow, policy-safe messaging — not raw LLM replies.

Positioning (POC): “AI sales inbox for Bangladeshi Facebook shops” — comment or DM in Banglish → verified price/stock → delivery/COD → lead handoff. Local language and local commerce rules are the whole point; nothing else is being claimed at this stage.

Deterministic (never LLM-only): price, variants, stock, shipping, order total, COD/refund rules, human assignment.

Recommended first MVP

One Page · one vertical · one inbox · Bangladesh
  1. Connect Page + webhook (messages, message_echoes, feed)
  2. CSV / paste-post catalog; merchant confirms prices & delivery rules
  3. AI answers in Banglish / Bangla / English — text only
  4. Comment on a post → private reply → same AI thread
  5. Collect variant, qty, phone, address into a lead
  6. Low confidence, or any image/voice attachment → human inbox

Production message path

Meta Webhook (messages | message_echoes | feed)
→ verify signature → idempotent event store (mid / comment_id)
→ resolve/create conversation → queue (per conversation, serialized)
→ echo?  → mark human takeover, stop
→ comment? → private reply, then normal thread
→ conversation-state gate → tools (catalog/rules) → LLM
→ re-check state → Send API → audit trail

Risks

RiskSeverityWhyControl
Meta app review & Business Verification High Advanced Access needs a verified business (trade licence, verified domain, privacy policy URL, data-deletion callback, demo video). Weeks, and it is a paperwork problem, not a code problem. Start verification on day 1, in parallel with Phase 1. Build on a test Page in Dev mode meanwhile.
Merchant replies from Facebook's own Page Inbox High Merchants will keep using the native FB inbox. Without message_echoes the bot replies on top of a human — the single most embarrassing production failure. Subscribe message_echoes; a merchant-sent echo forces pending_human.
Banglish comprehension High Most messages are romanized Bangla. Cheap open models are weakest exactly here, and it is the quality dimension the product rests on. Score candidates on ~200 real inbox messages before locking the prompt. Keep the LLM behind a thin client so the model is swappable.
Wrong price/stock High RAG goes stale Product/inventory API tools
Human takeover race Medium Bot + human double reply bot → pending_human → human states
Webhook dup / out-of-order Medium Meta retries; two fast messages can process concurrently Idempotency on mid + a Redis lock keyed on conversation_id around the agent job. Note: BullMQ's per-key concurrency (Groups) is a paid BullMQ Pro feature — plain BullMQ will not serialize per conversation for you.
Merchant has no catalog Medium Most BD f-commerce sellers keep stock in their head or in post captions. "Upload a CSV, then confirm every row" is where onboarding stalls. Make paste-post-link the primary import path. Allow a zero-catalog mode: AI answers delivery / COD / hours / qualification only, escalates every price question.

Human takeover state machine

bot → trigger → pending_human → claim → human → release/timeout → bot. Send gate reads state before every outbound message.

Knowledge layers

Catalog/policies = facts (tools). Docs/FAQ = RAG. Chat memory = context only. No exact product match → clarify or transfer, never invent price.
