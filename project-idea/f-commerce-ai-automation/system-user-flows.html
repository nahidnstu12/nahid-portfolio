Merchant onboarding flow

First-time setup until AI is allowed to reply.

1
Merchant Sign up / log in
Better Auth creates user + workspace (tenant). Empty dashboard.
2
Connect Facebook
OAuth → select Page → store encrypted Page token + Page ID. Subscribe webhooks. Settings show “Connected” + last webhook time.
3
Import catalog
CSV upload and/or paste post link → draft products. Merchant edits price, variants, stock.
4
Confirm products
Status draft → confirmed. Only confirmed rows are visible to AI tools.
5
Shop rules
Delivery fee, COD on/off, return/delivery text. Saved to shop_rules.
6
Enable AI
Toggle blocked until ≥1 confirmed product + delivery rule exists. New inbound threads default to bot mode.
Sign up → Connect Page → Catalog (confirm) → Shop rules → Enable AI → Live

Catalog & “paste link” flow

CSV path

  1. Upload CSV
  2. Preview rows in table
  3. Fix errors → save as draft
  4. Bulk “Confirm selected”

Post link path (optional POC)

  1. Paste FB post URL
  2. System fetches caption/image (Page token)
  3. LLM maps to draft fields
  4. Merchant edits → Confirm

AI agent path: customer asks “dress er dam?” → tool search_products → only confirmed matches → reply with DB price, not guessed text.

Customer message flow (happy path)

A
Customer Sends DM on Page Messenger
e.g. “M size ache? delivery koto?”
B
Meta POST webhook to your server
Next verifies signature, dedupes mid, saves message, enqueues job.
C
Worker Loads conversation
Takes a Redis lock on conversation_id (one job at a time per thread). If mode is human or pending_human → skip AI, notify inbox only. If bot → continue.
C2
Attachment gate (POC)
Message has an image, voice note or file? → pending_human, notify inbox, stop. The POC agent is text-only and must not guess at a photo.
D
Agent + tools
search_products, get_shop_policies, upsert_lead as needed. Reply in the same style the customer used — Banglish in, Banglish out.
E
Send gate
Re-read mode; if still bot, call Send API. Store outbound + audit.
F
Customer Sees reply in Messenger
Looks like the Page replied — may be AI or human; same channel either way.

Comment → DM flow

The other entry point, and in BD usually the bigger one. It converges on the same conversation record and the same state machine — it is not a second pipeline.

1
Customer Comments on a Page post
e.g. “dam koto?” under a boosted product post.
2
Meta POST webhook — feed field
Filter: comment-add on our own post only. Ignore comments by the Page itself, replies to our own comment, edits and deletes. Dedupe on comment_id — Meta retries.
3
Worker Optional public reply
Short fixed text the merchant can edit (e.g. “Inbox check korun”). Off by default if the merchant prefers.
4
Private Reply API
Opens a Messenger thread with that commenter. Once per comment, inside Meta's allowed window. After it lands, the ordinary 24-hour messaging window governs.
5
Converge on one conversation
Look up or create the conversation for that PSID + Page. Record source: comment and the post/product context so the agent knows what was being asked about.
6
Normal thread from here
Same agent, same tools, same bot / pending_human / human states, same lead capture.

When AI stops — human flow

TriggerSystemMerchant
No product match / empty catalog question request_human → mode pending_human Inbox badge “Needs human”; optional auto-reply “Someone will reply soon”
Customer sends an image or voice note Attachment gate → pending_human before the agent runs Inbox badge “Needs human”; POC agent is text-only
Merchant replies from Facebook's own Page inbox message_echoes event that we did not send → mode human automatically Nothing to click — the thread is simply theirs now until “Release to bot”
Customer angry, refund dispute, custom request Same or rule-based handoff Staff clicks Take over → human
Staff replying Worker ignores auto-reply while human Type in Inbox → Send API as Page
Issue resolved — Release to bot → bot

                                    └──────────────────► bot

Every outbound job checks mode twice: before the agent run and immediately before Send API — prevents a double reply after takeover. The mode check alone is not enough: also hold a Redis lock on conversation_id so two messages arriving together cannot run two agents on the same thread. Plain BullMQ has no per-key serialization (that is BullMQ Pro “Groups”).
