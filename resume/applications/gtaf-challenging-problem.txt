Tell us about a challenging problem you worked through.
How did you approach it, and what did you do when you got stuck?

Mazharul Islam Nahid
Application — Software Engineer (Web), Greentech Apps Foundation

---

Problem

We run a multi-tenant SaaS (Radius Directory) with a shared Redis/BullMQ central worker. It loads each live tenant from an APP_PATHS registry and runs that tenant’s queues, crons, and workers in one process.

With one live tenant, send-email worked. After a second tenant went live for testing (bikribd and rd-dev), production email failed for about two days for one tenant only. Crons for both still looked healthy, so it did not look like Redis or the worker process was simply dead.

Approach

I narrowed the problem before changing production code.

1. App-level check: triggered email without the central worker → send path worked. Mailer/app code was not the first suspect.
2. Local repro: ran two app instances under the central worker with Bull Board. Both tenants could send locally, so I stopped treating it as a unique code bug.
3. Server focus: checked what APP_PATHS the live worker actually saw. The running process still reflected a stale registry/env after tenant keys/paths had changed during testing.

Fixing that live registry/env mismatch and bringing the worker up on the intended mapping restored email. I won’t overclaim the exact OS/PM2 detail — I’m confident in the isolation path and the outcome.

When I got stuck

I list possible causes, then check them one by one. Console, debugger, and AI tools help me drop wrong guesses faster and shrink a big surface to a small fix — so I fix the real issue, not a random symptom.

Result

Both live tenants could send email again. Lesson: shared multi-tenant workers can fail per-tenant in subtle ways, and a clean local repro does not always catch a stale process environment on the server.
