1. The order SQL actually runs (not top-to-bottom)

You write SELECT first, but the engine runs it almost last. Memorize this pipeline — it explains 90% of "why doesn't this work?"

1FROM / JOINGrab & combine the tables
→
2WHEREFilter individual rows
→
3GROUP BYCollapse rows into groups
→
4HAVINGFilter the groups
→
5SELECTPick columns; window fns run here
→
6ORDER BYSort the result
→
7LIMITCut the list

What it explains: • WHERE can't see aggregates or SELECT aliases (runs before them) → use HAVING for aggregates. • ORDER BY can use a SELECT alias (runs after step 5). • Window functions can't go in WHERE (they're step 5) → rank in a CTE, filter outside.

2. A JOIN = following an arrow (foreign key)

Any something_id column is an arrow pointing at another table's id. Joining is just walking that arrow.

jobs.client_id → users.id · applications.job_id → jobs.id · milestones.project_id → projects.id
INNER = keep only rows where the arrow lands on a match.  LEFT = keep all left rows, put NULL where the arrow lands on nothing → that NULL is how you find "records with no related row" (WHERE right.id IS NULL).

3. An index = the index at the back of a book

Instead of reading every page (Seq Scan), flip to the sorted index and jump straight to the row (Index Scan).

Sorted → fast for =, ranges, and ORDER BY. Composite (a,b) reads left-to-right like a phone book sorted last-name-then-first: works for a or a+b, never b alone. Trade-off: faster reads, slower writes.

4. Pre-compute & store = the one idea behind "scalable design"

Three features in this repo are the same move: do the expensive work once, store the answer, then keep it fresh.

applications_count (denormalized column, kept fresh by a trigger) · average_rating (denormalized) · top_freelancers (materialized view, kept fresh by REFRESH). The cost is always the same: the stored copy can go stale.
