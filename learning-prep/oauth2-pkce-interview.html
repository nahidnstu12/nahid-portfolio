Foundation

First: authorization ≠ authentication

The single most common interview trip-up. Say this crisply:

  • OAuth 2.0 = authorization — "let this app do things on my behalf" (read my Google profile, my calendar). It's about access.
  • OpenID Connect (OIDC) = authentication — a thin layer on top of OAuth 2.0 that adds an id_token proving who the user is. It's about identity.

When you "Sign in with Google," you're using OAuth 2.0 as the transport and OIDC for the identity part. The id_token is what tells your app "this is user X, email Y."

Say this

"OAuth is delegated authorization; authentication is layered on via OpenID Connect's id_token. 'Login with Google' is really OAuth carrying an OIDC identity claim."

Vocabulary

The four roles

Every OAuth question is easier once you name the players. Here's the spec term and who plays it in a "Sign in with Google" on RadiusDirectory:

Resource Owner

→ the user

The person who owns the data and grants access. They approve the consent screen.

Client

→ RadiusDirectory app

The app requesting access. Registered with Google, has a client_id.

Authorization Server

→ Google (accounts.google.com)

Authenticates the user, shows consent, issues the code and tokens.

Resource Server

→ Google APIs (userinfo)

Holds the protected data; accepts the access_token to serve it.

A "public client" (a SPA or mobile app) cannot keep a secret — anyone can read its JS bundle. That single fact is why PKCE exists.

Why this changed

The Implicit Flow is dead

Old SPAs used the Implicit Flow: the authorization server put the access token directly in the URL fragment after redirect.

✗ Implicit Flow (deprecated 2025)

Token arrives in the URL:

https://yourapp.com/callback#access_token=eyJhbGciOi...

Why that's fatal:

  • Leaks via browser history — the full URL, token included, is saved.
  • Leaks via Referer header — any resource the page loads can see it.
  • Leaks via server/proxy logs — URLs get logged everywhere.
  • No way to verify the requester — a stolen code could be exchanged by anyone.

OAuth 2.0 Security BCP (RFC 9700, Jan 2025) and OAuth 2.1 drop Implicit entirely. The replacement for all clients: Authorization Code Flow + PKCE.

✓ Authorization Code + PKCE (now)

Nothing sensitive rides in the URL. The token comes back in a POST response body over a back channel. The URL only ever carries a one-time, useless-on-its-own code.

The mechanism

The flow, step by step

Three phases. The whole trick: a one-way hash sent up front, and a secret kept back until the end.

Phase 1 — Prepare the proof (before any redirect)

1

Generate code_verifier

The app invents a one-time random secret, 43–128 chars from [A-Z a-z 0-9 - . _ ~]. It never leaves the app.

const verifier = base64url(crypto.getRandomValues(new Uint8Array(32)));
// e.g. "dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk"
2

Derive code_challenge

A one-way SHA-256 fingerprint of the verifier. Safe to send in the open — you can't reverse a hash back to the secret.

code_challenge = base64url( SHA256( code_verifier ) )
code_challenge_method = S256   // always S256, never "plain"

Phase 2 — Get the code (front channel / browser redirects)

3

Redirect to /authorize

Send the user to the authorization server with the challenge (not the verifier), plus a state value for CSRF protection.

GET https://accounts.google.com/o/oauth2/v2/auth
  ?response_type=code
  &client_id=YOUR_CLIENT_ID
  &redirect_uri=https://yourapp.com/callback
  &scope=openid email profile
  &code_challenge=E9Melhoa2Ow...
  &code_challenge_method=S256
  &state=xyzABC123          // CSRF guard, checked on return
4

User authenticates & consents

Google logs the user in and shows the consent screen. It stores the code_challenge against the soon-to-be-issued code, to verify later.

5

Redirect back with authorization_code

A short-lived, one-time code lands in the URL. Yes — right there in the query string. Hold that thought.

https://yourapp.com/callback?code=A1b2C3d4&state=xyzABC123

Phase 3 — Exchange for the token (back channel / server-to-server POST)

6

POST to /token

The app sends the code plus the original code_verifier over a direct POST — not a browser redirect.

POST https://oauth2.googleapis.com/token
  grant_type=authorization_code
  code=A1b2C3d4
  redirect_uri=https://yourapp.com/callback
  client_id=YOUR_CLIENT_ID
  code_verifier=dBjftJeZ4CVP-mB92K27...   // the secret, first time it's sent
7

Server verifies the proof

Google recomputes SHA256(code_verifier) and compares it to the stored challenge from step 3.

if ( SHA256(code_verifier) === stored_challenge )  // ✓ continue
else                                              // ✗ error: invalid_grant

An attacker who stole the code from the URL doesn't have the verifier — so the exchange fails. That's the whole point.

8

Tokens returned in the body

Never in a URL — in the JSON response body of the POST:

{ "access_token": "...", "id_token": "...", "refresh_token": "...",
  "expires_in": 3600, "token_type": "Bearer" }

Key insight — the one line to remember

The authorization_code in the URL is one-time use and useless without the code_verifier, which never left the app. A one-way hash sent up front + a secret held back = the entire trick that replaced the implicit flow.

The payload

Three tokens, three jobs

Interviewers love asking you to distinguish these. Don't conflate them:

TokenPurposeFormatSent toLifetime
access_tokenAuthorize API calls ("what you can do")Opaque or JWTResource server, as Authorization: BearerShort (mins–1h)
id_tokenProve identity ("who you are") — OIDC onlyAlways a JWTConsumed by your app, not sent to APIsShort
refresh_tokenGet a new access_token without re-loginOpaqueAuthorization server onlyLong (days–∞)

A JWT is three base64url parts

header.payload.signature
// header:  { "alg": "RS256", "typ": "JWT" }
// payload: { "sub": "1029...", "email": "u@x.com", "exp": 1736... }  ← claims
// signature: RS256(header.payload, provider_private_key)  ← you verify with the public key

Gotcha interviewers plant

A JWT is signed, not encrypted. Anyone can base64-decode and read the payload — never put secrets in it. Trust comes from verifying the signature, not from the payload being hidden.

In RadiusDirectory

How NextAuth does this for you

You don't hand-roll PKCE — NextAuth v4 runs this whole flow for the Google and Facebook providers. What you configured:

// src/lib/auth.ts
providers: [
  GoogleProvider({
    clientId: process.env.GOOGLE_CLIENT_ID!,
    clientSecret: process.env.GOOGLE_CLIENT_SECRET!,
  }),
  FacebookProvider({ /* ... */ }),
  CredentialsProvider({ /* email/phone + password — NOT OAuth */ }),
]

What NextAuth handles under the hood for the OAuth providers:

  • Generates the code_verifier / code_challenge and the state value.
  • Stores them in short-lived, httpOnly cookies during the redirect round-trip.
  • Does the back-channel /token POST (the clientSecret above authenticates your server as a confidential client).
  • Verifies the id_token and hands you a normalized user in the jwt / session callbacks.

Nuance worth stating in an interview

Because RadiusDirectory does the token exchange server-side in Next.js (it has a clientSecret), it's technically a confidential client, so PKCE is defense-in-depth rather than strictly required. PKCE is mandatory for a pure browser SPA that can't hold a secret. Knowing which situation you're in is the senior-level answer.

Your Credentials provider is a different beast

The email/phone + password (and OTP) login is not OAuth at all — it's your own DB check, then NextAuth mints a session JWT (30-day expiry). Don't describe that path as OAuth; it's classic first-party credential auth. OAuth only governs the Google/Facebook buttons.

The follow-up they always ask

Where do you store the token?

Getting the token is half the interview; storing it safely is the other half.

LocationXSS riskCSRF riskVerdict
localStorageHigh — any script reads itNoneAvoid for tokens
JS memory (variable)Lower — gone on reloadNoneOK for access_token
httpOnly cookieSafe — JS can't read itNeeds SameSite / CSRF tokenBest for session / refresh

The consensus answer: keep the refresh/session token in an httpOnly, Secure, SameSite=Lax cookie so XSS can't exfiltrate it — which is exactly what NextAuth does for your session. Never localStorage for anything that grants access.

Say this

"localStorage is readable by any injected script, so a single XSS steals the token. I keep session tokens in httpOnly SameSite cookies and pair that with CSRF defenses — which is what NextAuth gives us by default."

Drill

Rapid-fire interview questions

Q. Why not just skip the code and return the token directly?

That is the dead implicit flow. Tokens in URLs leak via history, Referer, and logs. The code is a one-time throwaway that's worthless without the verifier, so a leaked URL isn't a breach.

Q. What does PKCE actually protect against?

Authorization code interception. On mobile/SPA a malicious app could grab the redirect code. Without the verifier it can't exchange it. PKCE binds the code to the client that started the flow.

Q. What's the state parameter for?

CSRF protection on the redirect. You generate it before /authorize and verify the returned value matches — stops an attacker forcing their code onto your session. It's separate from PKCE; you want both.

Q. S256 vs plain challenge method?

Always S256 (SHA-256 hash). plain sends the verifier as-is and defeats the purpose — only allowed for legacy clients that can't hash. An interviewer wants to hear "S256, never plain."

Q. Access token expired mid-session — what happens?

Use the refresh_token to silently get a new access_token from /token, no user re-login. Best practice is refresh token rotation — each refresh issues a new one and invalidates the old, so a stolen refresh token is detectable.

Q. Is a JWT encrypted?

No — signed. The payload is base64url, publicly readable. Security comes from signature verification, not secrecy. Don't store sensitive data in it.

Q. OAuth vs OIDC in one sentence?

OAuth 2.0 grants access (authorization); OIDC layers on top to prove identity (authentication) via the id_token. "Login with Google" uses both.
